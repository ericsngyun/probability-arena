## B1 — selection: partition before the limit, not a naive oldest-first `LIMIT`

`CryptoLifecycleTapeRecorder.classify_backlog` (`app/services/crypto_tape.py`) implements the typed partition `scripts/crypto_backlog_partition.py` only ever derived offline: `RETENTION_LOST` / `MISSING_REQUIRED_INITIAL_STATE` (cheap, monotone write-offs — timestamp or one birth-table lookup, no tick scan) versus `RECOVERABLE_NOW` / `OTHER_TYPED_REASON` (sub-horizon) / `UNRESOLVABLE_WINDOW_CLOSED` / `NOT_YET_DUE` (need one batched, indexed tick probe over a session-temp table to tell apart — never one round trip per token). `unreconciled_backlog` now classifies the FULL backlog before any per-pass `limit` is applied, then `_split_backlog_budget` reserves a small (10%, floor 1), bounded slice of `limit` for write-offs so they still get flushed (memorialised `final=True`, permanently excluded from later selection) without consuming a whole pass.

A subtlety found and fixed while implementing this: a never-reconciled backlog token (no `CryptoTokenBirthEvent` row yet — the majority of any real backlog) always reads `initial_liquidity_usd IS NULL` from the birth-table outer join, which is "no birth row exists yet", not "liquidity is unmeasurable". Naively treating that as `MISSING_REQUIRED_INITIAL_STATE` would misclassify almost the entire never-touched backlog as permanent write-offs. `classify_backlog` instead falls back to a batched lookup of each such token's EARLIEST persisted tick (mirroring `build_birth_event`'s own `sources.ticks[0].liquidity_usd` derivation) before deciding.

**Test:** `tests/test_crypto_backlog_selection_finality_001.py::test_unreconciled_backlog_prioritises_recoverable_over_writeoffs` reproduces the measured shape (20 RETENTION_LOST write-offs older than 3 RECOVERABLE_NOW tokens) and proves a room-of-5 selection still includes all 3 recoverable tokens — which a naive oldest-first `LIMIT` would not. `test_unreconciled_backlog_still_reserves_a_writeoff_slice` proves write-offs are not starved to zero either. Both fail when reverted (verified via `git stash`).

## B2 — finality: `permanently_missing_evidence` replaces a disproved `still_recoverable`

`compute_survival` (`app/services/crypto_tape.py`) used to leave `final=False`, `finality="still_recoverable"` when the 24h window closed with no answer and retention hadn't yet expired the evidence — on the theory that a future pass might still recover it. That theory is false: `_load_sources` (this call's own caller) already loads EVERY tick a token has, unfiltered by time, and every tick writer sets `observed_at=now()` at write time — so once `now >= closing_edge`, any future tick lands even further past the tolerance window than this call already searched. The negative result is proven, not pending. Replaced with `final=True`, `finality="permanently_missing_evidence"`, distinguished from `observed_terminal` (a real answer exists) and `retention_lost` (evidence was pruned), reusing the existing per-horizon `"no_observation_in_window"` missing-cause vocabulary rather than inventing new prose.

**Test:** `tests/test_crypto_tape_001.py::TestSurvivalLabels::test_final_when_window_closed_and_evidence_provably_missing` (renamed/rewritten from the old regression pin) plus `tests/test_crypto_backlog_selection_finality_001.py::test_scheduled_pass_finalises_a_permanently_missing_evidence_backlog_token` (end to end through the scheduled path). Both fail when reverted.

## B3 — frontier: recoverable age, not the oldest row regardless of recoverability

`recoverable_backlog_summary` (reusing `classify_backlog`, never re-deriving the predicate) reports `recoverable_backlog_count`, `oldest_recoverable_due_at`, `oldest_recoverable_age_seconds`, `recoverable_at_retention_risk`, and `writeoff_count` by reason. `run_once` computes this PRE-PASS (same timing as the existing raw frontier, and for the same reason: measuring it after `_assemble_pass` would report "how good it looks now that we just fixed it" instead of "how far behind was the reconciler when this pass started"). `run_scheduled_reconciliation`'s `backlog_expiring` gate now checks the recoverable frontier instead of the raw oldest-row frontier, which was previously permanently on once any write-off ever accumulated (measured: frontier ~204h vs a 162h threshold, permanently failed).

**Test:** `tests/test_crypto_backlog_selection_finality_001.py::test_five_repeated_passes_over_unrecoverable_tokens_do_not_advance_frontier_or_duplicate` — five scheduled passes over 5 pure-write-off tokens: the recoverable frontier stays `None`/0 throughout (never falsely advances or falsely alarms), `status` never becomes `backlog_expiring`. Fails when reverted.

## B4 — no repeated write-off writes

Reproduced and closed as a corollary of B1 + the pre-existing `exclude_final=True` / `skip_redundant_when_final=True` machinery: once B1 correctly prioritises write-offs into selection (instead of them being crowded out or, alternately, dominating every pass), the first pass that reaches a write-off token runs `compute_survival`, sets `final=True` (B2), and `exclude_final=True` drops it from every later selection query at the SQL level — no later pass re-derives or re-writes it. `skip_redundant_when_final=True` (scheduled path only) additionally skips the redundant lifecycle-snapshot/actor-observation append on any later pass that might otherwise touch an already-final token.

**Test:** the same five-pass test above asserts, after 5 scheduled passes over 5 write-off tokens: exactly 1 `CryptoTokenSurvivalOutcome` row per token (not 5), exactly 5 `CryptoTokenLifecycleSnapshot` rows total (not 25), exactly 5 `CryptoTokenActorObservation` rows total (not 25). Idempotency is SEMANTIC (grounded in `final=True` + state-driven selection), not merely unique-key-constrained.

## B7 — the operator migration path made executable

`docs/EVO_X2_RUNBOOK.md`'s deployment-update sequence used `$DB_PATH` (defined nowhere in this repo) and `sqlite3 "$DB_PATH" "PRAGMA integrity_check"`, which — with `$DB_PATH` unset — expands to `sqlite3 "" "PRAGMA integrity_check"`: SQLite's `""` filename convention opens a TEMPORARY database and prints `ok` with exit 0 having inspected nothing. Worse, `sqlite3` is not installed on EVO-X2 at all. Replaced with two new, tested `app.cli` commands using the application's own database resolution:

- `db-schema-report` — resolved database path (secret-free), current/head Alembic revision, and `SCHEMA_MATCH`/`SCHEMA_BEHIND_CODE`/`SCHEMA_AHEAD_OF_CODE` status; fails (prints `FAIL`, exit 1) if the resolved path is empty or an in-memory/blank DSN. Exit 0 iff `SCHEMA_MATCH`.
- `db-integrity-check` — resolved database path, then a real `PRAGMA integrity_check` through the app's own engine; same empty-path guard; reports measured duration (documented ~7m18s at the current EVO-X2 database size — not fast, do not run casually inside a tight maintenance window).

## B8 — `SCHEMA_AHEAD_OF_CODE` distinguished from `SCHEMA_BEHIND_CODE`

`app/db.py::ensure_schema_current` tested only `current == head`, so a database AHEAD of the code (e.g. `0028` applied, then the deploying commit reverted) raised the identical `MigrationRequiredError` as one behind, with remediation text ("run `alembic upgrade head`") that is a no-op when ahead — an operator following it loops forever. `_schema_status` now classifies `SCHEMA_MATCH` / `SCHEMA_BEHIND_CODE` / `SCHEMA_AHEAD_OF_CODE` by walking the code's own revision history from its head; a stamped revision the code's history walk can never reach (either unknown to this code's `alembic/versions/` entirely, or simply downstream) is classified AHEAD. A new `SchemaAheadOfCodeError` (deliberately NOT a `MigrationRequiredError` subclass, so an `except MigrationRequiredError` catch site never silently swallows the AHEAD case) names the real decision: redeploy the newer code, or downgrade — never auto-downgrade. The `0028` downgrade procedure is documented and independently measured: 3.25s wall time, 0.157s lock hold, an 18-character value preserved intact through a downgrade+reupgrade round trip, and the `PRAGMA foreign_keys=OFF` dependency this batch rebuild relies on (production carries 7,345 pre-existing dangling FK rows).

**Test:** `tests/test_migrations.py::test_ensure_schema_current_raises_distinct_error_when_database_is_ahead_of_code` and `test_ensure_schema_current_still_raises_migration_required_when_genuinely_behind` (regression pin the other direction). Both fail when reverted.
